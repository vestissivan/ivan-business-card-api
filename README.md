# Иван Темников · GraphQL business card

Backend-тестовое: **TypeScript, Node.js 24, NestJS 12, Prisma 7, GraphQL / Apollo Sandbox, Docker, Git**.

## Запуск с нуля

Самый короткий путь, нужен только Docker:

```sh
docker compose up --build
```

Откройте **http://localhost:3000/graphql**. Apollo Sandbox содержит готовый запрос; нажмите Run. Аккаунт Apollo не требуется. Проверка готовности: **http://localhost:3000/health**.

Локально, Node.js 24:

```sh
npm ci
npm run build
npm start
```

SQLite-файл, таблицы и данные создаются **при старте автоматически**. `.env`, внешний сервер БД и ручной seed не нужны. В Compose файл сохраняется в именованном томе `profile-data`. `DATABASE_URL=file:/absolute/path/profile.db` задаёт другой путь. `PORT` по умолчанию 3000.

```graphql
query BusinessCard {
  profile {
    name
    description
    links { label url }
    skills { name }
    experience {
      company
      position
      period
      startDate
      endDate
      achievements
    }
    projects { name description url }
  }
}
```

## Архитектура и решения

- **GraphQL presentation:** `profile.resolver.ts`, `profile.types.ts`. Code-first schema, явные типы и nullability. Только запросы: публичный API не изменяет данные. Introspection включена для Sandbox.
- **Application service:** `profile.service.ts` преобразует запись в DTO и хранит Promise результата в рамках одного запроса (`Scope.REQUEST`). Несколько обращений/алиасов не создают повторные загрузки профиля.
- **Repository:** `profile.repository.ts` использует типизированный Prisma Client и загружает четыре упорядоченные связи через `include`. Это не запрос на каждую строку: полный профиль требует до **пяти SELECT**, независимо от числа навыков и проектов. Тест с 83 проектами и двумя GraphQL-алиасами проверяет этот предел по реальным SQL-событиям Prisma. Для этой небольшой визитки намеренно выбран простой eager loading вместо look-ahead-парсера GraphQL и дополнительных DataLoader-слоёв. Компромисс — связанные данные загружаются и при запросе одного имени.
- **Database lifecycle:** `PrismaService` применяет миграции до подключения и выполняет transactional seed до готовности HTTP-сервера. `migrate.ts` читает отсортированные SQL-файлы, применяет новые внутри SQLite-транзакции и сохраняет SHA-256 в отдельном `__app_migrations`. Изменённая уже применённая миграция останавливает запуск. Это небольшой собственный runner для одинакового старта в контейнере и serverless; таблицу `_prisma_migrations` он не имитирует. Prisma CLI используется для генерации клиента и SQL/diff. `prisma migrate deploy` к этой БД применять не следует: жизненным циклом миграций владеет startup-runner.
- **Seed:** стабильные ID и `upsert` в одной транзакции; повторный старт не дублирует строки. Seed обновляет известные записи и не удаляет посторонние. `npm run db:init` вручную повторяет ту же инициализацию после build.
- **SQLite**: визитка доступна только для чтения, база невелика, внешние учётные данные не требуются. Индексы `(profileId, sortOrder)` обслуживают связи; foreign keys, WAL и busy timeout включены. Для многопользовательского продукта с изменяемыми данными выбрал бы отдельный PostgreSQL и обычный deployment migration job.
- **Serverless preview:** тот же код миграций и seed, база создаётся в `/tmp`. При новом изолированном cold start публичные данные восстанавливаются; постоянного хранения пользовательских изменений здесь нет, API их не принимает. Контейнерный вариант сохраняет БД в томе.
- **Ошибки и доступ:** нет пользовательского SQL, мутаций, секретов и приватных материалов. Stack traces не выдаются в GraphQL, CORS разрешён для Apollo Sandbox. Готовность проверяется настоящим `SELECT 1`.

## Данные о кандидате

Это самостоятельные проекты и портфолио, а не выдуманная трудовая история. Единственная запись `experience.company = "Самостоятельные проекты"` явно обозначает формат. Продолжительность автоматизации — подтверждённые кандидатом два года. Точные даты не предоставлены, поэтому `startDate`/`endDate` равны `null`, а `period` поясняет это словами. Указанный срок не выдаётся за коммерческий стаж TypeScript/Python.

Публичные ссылки на TORQ WORKS, PRISM/9, СЛОЙ и резюме приведены с разрешения кандидата. Результаты Python-бота (84 источника и 18 тестов перед одним из выкатов) взяты из подтверждённого проекта. Неподтверждённые работодатели, бизнес-метрики и сертификаты не добавлены.

## Проверки

```sh
npm run db:check
npm test
```

10 интеграционных тестов работают с настоящей временной SQLite и HTTP-приложением: чистый запуск, вложенный профиль, fragments/aliases/directives, валидация полей, отсутствие мутаций, health, Sandbox, кеш в рамках запроса, ограничение SQL-запросов при росте списка, повторный старт и отказ при изменении миграции.

GitHub Actions дополнительно собирает Docker-образ, запускает его без подготовленной БД, выполняет HTTP smoke test, перезапускает контейнер и повторяет проверку. Секреты для CI не нужны.

## Изменение схемы

Редактируйте `prisma/schema.prisma`; создавайте следующую SQL-миграцию средствами `prisma migrate diff` между предыдущей схемой и новой. Старые применённые SQL-файлы не редактируйте. После первой миграции `db:check` сравнивает именно начальную схему; при добавлении версии нужно расширить проверку до полной истории. `npm run build` генерирует Client и копирует миграции рядом с исполняемым кодом. Приложение остановится, если миграция или seed не прошли.
